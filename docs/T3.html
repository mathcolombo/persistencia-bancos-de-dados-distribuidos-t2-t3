T3 — Evolução, transações e recuperação

Use perfis independentes. A migração usa cópia de clientes; a Saga possui massas por cenário; PITR possui origem e destino separados. Preserve T1 e T2.

Parte A — Migração com Flyway

A1. Antes da expansão

python lab.py stop
python lab.py up migration
python lab.py client python migration v1 2

Troque python por java no argumento de linguagem para JDBC. A base começa com 200 clientes: 18, 42 e 198 registros auxiliares (1000 a 1197). O exercício que insere 55 adiciona uma linha, totalizando 201; não é um erro de carga.

No pacote do aluno, complete migrations/expand/V1__expand.sql antes de aplicá-la. A função de trigger deve copiar a autoridade contato_email para email, inclusive NULL, na mesma transação. Remova o marcador TODO_ALUNO depois de implementar. O comando de expansão recusa um arquivo ainda marcado como incompleto.

python lab.py migrate expand
python lab.py sql migration -q "UPDATE cliente SET contato_email='ana.nova@exemplo.test' WHERE id=42; INSERT INTO cliente VALUES(55,'Nulo',NULL,NULL); SELECT id,contato_email,email FROM cliente WHERE id IN (42,55);"

As duas colunas devem coincidir para 42 e ser nulas para 55. Flyway registra baseline explícito versão 0 para a base pré-existente e aplica V1. Não executar clean, não editar uma migração já aplicada. Se uma alteração no código do exercício exigir novo ensaio, salve evidências e reinicie somente o perfil migration.

A2. Clientes concorrentes e backfill

Abra três terminais na raiz do kit. No terminal 1:

python lab.py client python migration v1 30

No terminal 2:

python lab.py client python migration v2 30

No terminal 3, enquanto os anteriores rodam:

python lab.py client python backfill 2
python lab.py sql migration -q "SELECT * FROM lab_checkpoint;"
python lab.py client python backfill 100
python lab.py sql migration -q "SELECT count(*) FROM cliente WHERE email IS DISTINCT FROM contato_email;"

Java aceita os mesmos argumentos. Cada lote atualiza no máximo 25 linhas e grava seu checkpoint na mesma transação. O primeiro comando encerra após dois lotes; o segundo retoma. O limite 100 é um máximo de lotes, não quantidade de linhas.

Para demonstrar repetição de lote, antes de terminar a convivência, grave o checkpoint observado, execute UPDATE lab_checkpoint SET last_id=0 WHERE id=1; e rode backfill 1, seguido de backfill 100. A cópia usa a coluna antiga autoritativa no próprio UPDATE, sem guardar em memória uma versão antiga do valor. A contagem final de divergências deve ser zero. Registre o efeito de repetir esse lote.

Espere os dois clientes terminarem. Eles registram leituras/escritas e duração no log; lab_ops registra as operações bem-sucedidas. Erros interrompem o cliente com saída diferente de zero e ficam no log, não são contados como sucesso. Consolide tentativas, sucessos e erros a partir dos dois registros.

A3. Janela de retorno e contração

python lab.py gate retirar
python lab.py gate retorno
python lab.py client python migration v1 1
python lab.py gate janela
python lab.py client python migration v2 10
python lab.py gate liberar
python lab.py migrate contract
python lab.py client python migration final 2

O gate usa lock compartilhado por operação e exclusivo na mudança de fase. retirar impede novas operações v1 e aguarda as em andamento. retorno permite o teste controlado de v1; janela o retira novamente e zera a contagem. Dez ciclos de v2, um por segundo, preservam o formato antigo durante a janela. liberar exige backfill consistente e retorno demonstrado, então suspende os clientes de compatibilidade. A contração remove trigger e coluna antiga; somente depois o cliente final é admitido.

Esta passagem pode introduzir espera/indisponibilidade no laboratório e não demonstra zero downtime universal. Explique por que usar uma barreira explícita simplifica o ensaio e quais mudanças seriam necessárias para requisitos de produção. Não confundir ausência de erro de DDL com ausência de bloqueios.

python lab.py sql migration -q "SELECT version,description,success FROM flyway_schema_history ORDER BY installed_rank;"
python lab.py sql migration -q "SELECT versao,count(*),max(duracao_ms) FROM lab_ops GROUP BY versao;"
python lab.py sql migration -q "SELECT column_name FROM information_schema.columns WHERE table_name='cliente' ORDER BY ordinal_position;"

Em uma cópia nova do perfil, python lab.py test migration --linguagem python executa automaticamente o percurso para validação docente. Não substitui a interpretação do grupo.

Parte B — Saga

B1. Completar a lógica

python lab.py stop
python lab.py up saga

Complete proxima, apos_pagamento e liberar_sql na linguagem escolhida. A estrutura de persistência e chamadas já existe. Estados: PENDENTE → RESERVADO → PAGAMENTO_CONFIRMADO → CONFIRMADO; rejeição conhecida leva a COMPENSACAO_PENDENTE → CANCELADO.

A liberação deve alterar reserva ATIVA para LIBERADA somente uma vez, retornando a linha realmente alterada. O serviço devolve estoque apenas quando houve transição. A transação local engloba estado e devolução. Não basta verificar um booleano em memória.

Cada op cria uma massa de estoque isolada começando em cinco unidades para o produto 10. Assim, os cenários não consomem o saldo uns dos outros. O orquestrador usa lock por intenção para não executar simultaneamente dois avanços da mesma Saga. Cada serviço mantém sua transação própria; não há transação única atravessando os três bancos.

B2. Cenários manuais

python lab.py client python saga grupo1_s1 aprovado
python lab.py client python snapshot grupo1_s1
python lab.py client python saga grupo1_s2 rejeitado
python lab.py client python snapshot grupo1_s2
python lab.py client python liberar grupo1_s2
python lab.py client python liberar grupo1_s2

Esperado: S1 CONFIRMADO, estoque 4, reserva ATIVA, uma cobrança. S2 e repetições: CANCELADO, estoque 5, reserva LIBERADA, zero cobranças. Trocar o modo para a mesma intenção é rejeitado.

Falha após reserva, antes de registrar avanço local:

python lab.py client python saga grupo1_s4 rejeitado after-reserve
python lab.py client python saga grupo1_s4 rejeitado
python lab.py client python snapshot grupo1_s4

Falha após compensação, antes de registrar conclusão na Saga:

python lab.py client python saga grupo1_s5 rejeitado after-release
python lab.py client python saga grupo1_s5 rejeitado
python lab.py client python snapshot grupo1_s5

Os comandos com falha injetada terminam com código 17 e mensagem FALHA_INJETADA. É esperado. Execute a retomada sem o último argumento. O novo processo consulta o estado persistido, repete a mesma intenção e não deve duplicar o efeito. S4 e S5 terminam CANCELADO com estoque cinco.

Repetição de sucesso:

python lab.py client python saga grupo1_s1 aprovado
python lab.py client python snapshot grupo1_s1

Continua com uma cobrança, uma reserva e estoque quatro. Use outros IDs em novos ensaios para não confundir histórico. Todos os comandos aceitam java no lugar de python.

O teste python lab.py test saga --linguagem python executa S1–S6 com IDs novos e confere os quatro estados/saldos nos bancos. Timeout de pagamento e 2PC permanecem análises orientadas, em docs/analises_T3.md; não há transação preparada real obrigatória.

Parte C — Backup físico e PITR

C1. Preparar backup

python lab.py stop
python lab.py pitr backup

Cria origem exclusiva, insere id 1 e conclui pg_basebackup com WAL de consistência. pg_verifybackup verifica o backup. Um backup anterior não é sobrescrito: para novo ensaio, usar reset pitr depois de preservar evidências.

C2. Operações e incidente

python lab.py pitr incidente

O comando confirma id 2, cria um ponto nomeado, confirma id 3 e confirma a exclusão controlada. Guarda os instantes observados externamente, força troca de WAL e aguarda o segmento final aparecer no arquivo. O resultado informa um nome como lab_123....

No pacote do aluno, copie o nome informado para exercicios/pitr.json:

{"nome_do_ponto": "lab_NOME_REAL_INFORMADO_PELO_COMANDO"}

Não usar literalmente o exemplo. O pacote de referência usa AUTO, que seleciona o marcador do experimento atual.

O relógio de RTO já começou no incidente. O tempo de editar o arquivo e iniciar o comando seguinte faz parte da recuperação operacional; não alterar timestamps para omiti-lo.

C3. Restaurar e medir

python lab.py pitr restaurar
python lab.py pitr medir

A base é copiada para volume separado, configurada com recovery_target_name e recovery.signal; recebe somente WAL arquivado. Ao alcançar o ponto, PostgreSQL finaliza a recuperação automaticamente pela ação configurada. Não fazer promoção manual para esconder alvo não atingido.

Verificações: origem continua com zero linhas; destino contém ids 1 e 2, não contém id 3; log contém o marcador; destino saiu da recuperação. A ausência de 3 mostra que também se deixou de recuperar uma operação legítima posterior ao alvo.

Arquivos gerados: pitr-controle.json, pitr-operacoes.csv, pitr-metricas.json e logs de comandos. O controle é externo às instâncias. Não reinicie o host entre etapas: os cálculos usam o mesmo relógio monotônico. Se isso ocorrer, registre o ensaio como inválido para tempo e faça outro experimento com identidade nova.

RTO observado: incidente até validação final. Janela de perda observada: incidente menos a última confirmação legítima recuperada (id 2). Metas didáticas: 600 e 60 segundos. Estar fora da meta não invalida automaticamente o procedimento; exige análise. A medição não garante RPO/RTO em produção.

C4. Falta de WAL — teste docente opcional

Em ensaio próprio, depois de pitr incidente e antes do restore normal:

python lab.py test pitr-wal-ausente

Esse teste usa outro destino e um arquivo WAL vazio, preservando o backup e o WAL originais. Só aceita como resultado esperado a mensagem de recuperação encerrada antes do alvo. Depois pode executar o restore normal; o tempo extra permanece incluído no RTO daquele ensaio. Não usar este ensaio de falha para comparar desempenho com um restore sem falha.

Se o teste não observar a mensagem esperada, ele falha e exige investigação; não registra sucesso apenas porque o contêiner ficou indisponível. Os volumes auxiliares são removidos por reset pitr.
