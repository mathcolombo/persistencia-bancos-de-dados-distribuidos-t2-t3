# T2 — Distribuição e consistência

Preserve a entrega T1. Execute sharding como simulação, replicação como experimento real e CAP/garantias de sessão como análise de cenários.

## 1. Sharding

Complete `modulo`, `sucessor` e `movidas` em `exercicios/respostas.py` ou `Respostas.java`. As funções SHA-256, geração das chaves e exportação CSV já estão prontas. Java trata o hash de 64 bits **sem sinal**, mesmo armazenando-o em `long`: usar comparação e resto sem sinal.

Convenções: chaves K:0000 a K:0999; pontos `N:A:00` etc.; um ponto por nó ou 16 pontos por nó. Em caso de igualdade, o ponto é dono da chave; além do último ponto, retorna ao primeiro. Os pontos antigos não mudam quando D entra. A faixa tem A=0–333, B=334–666 e C=667–999; nela, o ensaio não adiciona D. Sua movimentação é zero por comparar a configuração consigo mesma, não por demonstrar expansão sem transferência.

```text
python lab.py client python shard evidencias/execucoes/shard-python-1
python lab.py client python shard evidencias/execucoes/shard-python-2
```

Ou:

```text
python lab.py client java shard evidencias/execucoes/shard-java-1
python lab.py client java shard evidencias/execucoes/shard-java-2
```

Compare CSVs das duas execuções na mesma linguagem: mesmas mil chaves e destinos. Conte somente mudança de **nó físico**. Expliquem desequilíbrio e hot key sem supor que uniformidade de chaves equivale a uniformidade de carga. Executem `python lab.py test unit` para verificar regras do anel e a massa. Esse teste importa o código Python; grupos Java podem usar os CSVs e os critérios de aceite, ou o professor pode executar a comparação de linguagens descrita na validação.

## 2. Subir a réplica

```text
python lab.py stop
python lab.py up replica
python lab.py sql primary -q "SELECT pg_is_in_recovery();"
python lab.py sql standby -q "SELECT pg_is_in_recovery();"
python lab.py sql primary -q "SELECT application_name,state,sync_state FROM pg_stat_replication;"
```

Esperado: `f` no primário, `t` no standby e aplicação `standby1` em streaming. A primeira inicialização clona o primário com `pg_basebackup`. Não promover o standby. Se não iniciar, consultar `docker compose logs primary standby`.

## 3. Observar três modos

```text
python lab.py client python replica async
python lab.py client python replica on
python lab.py client python replica remote_apply
```

Substitua a linguagem por `java` para a versão JDBC. Os identificadores são 2001, 2002 e 2003. Cada comando pausa replay, **confirma que a pausa foi efetivada**, faz a escrita em conexão independente, observa a leitura e retoma replay no encerramento normal e nas falhas tratadas.

| Modo | Durante replay pausado | Após retomada |
|---|---|---|
| async | Commit pode confirmar; standby ainda sem a linha | Linha deve aparecer |
| on, com standby síncrono | Exige flush remoto, mas pode confirmar sem replay | Linha deve aparecer |
| remote_apply | Cliente deve estar esperando após 3 segundos | Commit conclui e a linha aparece |

O roteiro mede a duração no próprio cliente com relógio monotônico. O tempo de iniciar Docker/JVM não é a latência do commit registrada. Não comparar latências como benchmark. As consultas são novas transações; um snapshot antigo poderia continuar vendo o estado anterior.

Pausar replay não impede recebimento de WAL, não simula uma partição de rede e não representa perda de máquina.

## 4. Timeout e resultado desconhecido

```text
python lab.py client python replica timeout
```

O caso usa id 2004 e um limite menor que a pausa. O cliente registra sua observação e consulta o primário pelo **mesmo identificador** depois de retomar replay. Dependendo do momento e da API, uma interrupção da espera pode produzir aviso ou erro; registrar o resultado observado. Não assumir que timeout significa rollback nem criar outra identidade para a mesma intenção.

## 5. Recuperação de uma interrupção do processo

Se o usuário fechar o terminal ou matar um contêiner, o bloco de limpeza do cliente pode não executar. Em outro terminal:

```text
python lab.py sql standby -q "SELECT pg_wal_replay_resume();"
python lab.py sql primary -q "ALTER SYSTEM SET synchronous_standby_names='';"
python lab.py sql primary -q "SELECT pg_reload_conf();"
python lab.py sql standby -q "SELECT pg_get_wal_replay_pause_state();"
python lab.py sql primary -q "SELECT * FROM evento_lab ORDER BY id;"
```

Use `reset replica --confirmar APAGAR-LAB` somente após salvar os logs, quando precisar repetir os IDs. Não limpar a tabela enquanto houver commit pendente.
